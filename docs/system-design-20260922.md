# 星光计划系统设计与需求追踪基线

版本：2026-09-22。依据项目交接、产品激活、技术改造、内容发布建议、已有代码和最新确认整理。本文是可执行的产品/工程基线，不是第三方认证或“永无缺陷”保证。未找到此前提到的其他公司完整系统设计文件，不对未读取的文件作符合性结论。

## 1. 产品边界

学生通过机会、活动、知识内容持续成长，形成可验证的成长档案；企业发布机会与真实问题，组织青年实践并评审成果；运营方审核企业活动和内容，发布自办项目，维护秩序和内容质量。

不做即时招聘聊天，不做在线投递中介，不代付奖金，不承诺录用。简历通过企业提供的邮箱投递，学生可自愿附带独立公开成长链接。

本次新增正式组队比赛：每人独立账号、独立资格审核；队长向指定邮箱生成邀请，受邀人登录后主动接受；平台保存团队成果和评审结果，企业线下兑现奖金/推荐。

## 2. 模块与对象

| 模块 | 核心对象及已有行为 | 本次处理 |
|---|---|---|
| 身份 | 学生/企业邮箱密码；运营密钥；会话、重置邮件、限流 | 沿用既有鉴权，不放开真实后台 |
| 资料 | 学生资料、私有简历、结构化提取、企业认证 | “主页标题”改为“一句话介绍”；不写入默认学校和姓名 |
| 机会 | 企业发布岗位、筛选、收藏、企业岗位页、邮件投递 | Logo 固定盒子；标题与摘要限行，详情保留全文 |
| 活动 | 发布、运营审核、个人报名、发布方审核、日历 | 普通活动兼容；新增竞赛任务书与团队流程 |
| 内容 | 图文/视频、富媒体块、封面、点赞评论、发布方回复 | 保留；统一列表卡片高度与封面比例 |
| 竞赛 | 任务书、报名资格、团队、定向邀请、成果、评审、认证 | 新增完整纵向流程 |
| 成长 | 手动经历、平台认证、排序、可见性、公开分享 | 竞赛终审后为每位成员生成认证，默认私密 |
| 治理 | 三类发布审核、企业认证、诚信记录、审计 | 竞赛资格/成果由主办方审核，不与运营发布审核混用 |
| 运维 | SQLite 磁盘库、文件存储、备份恢复、发布回滚 | 新表采用增量建表，生产数据不重置、不重新播种 |

## 3. 权限矩阵

| 操作 | 学生 | 企业 | 运营 |
|---|---|---|---|
| 查看公开任务书 | 可以 | 可以 | 可以 |
| 审核企业发布的活动/内容 | 否 | 否 | 可以 |
| 审核企业活动报名 | 否 | 仅自己发起 | 否 |
| 审核自办活动报名 | 否 | 否 | 星光计划自办 |
| 创建/加入团队 | 本人报名通过后 | 否 | 否 |
| 邀请成员/提交成果 | 仅队长 | 否 | 否 |
| 查看团队成果 | 本团队成员 | 本场主办企业 | 星光计划自办 |
| 评审与记录奖励 | 否 | 本场主办企业 | 星光计划自办 |
| 对外公开个人认证 | 本人决定 | 否 | 否 |

权限由服务端鉴权与活动 owner_id 判断，不信任前端 role、publisher 或任意团队 ID。企业成果不会因为进入运营后台就默认对运营评审台开放。

## 4. 竞赛任务书

`activity.challenge` 为可选配置，旧活动不存在此字段时保持普通活动。

字段：enabled、problem、eligibility、deliverables、criteria、rewards、registrationDeadline、submissionDeadline、resultsDate、teamMin、teamMax。

必须明确：真实问题及约束、可提供资源、交付材料格式、评审标准及权重、奖励条件与兑现主体。循环经济提供可编辑参考结构，不自动发布、不编造日期、合作企业、奖金额或获奖者。

人数取 1–20 的整数区间，默认 2–6；日期按北京时间当天 23:59:59.999 截止，顺序为报名截止 ≤ 成果截止 ≤ 预计公布。竞赛普通活动日期是活动场次信息，报名以任务书截止日期为准。

## 5. 状态与业务规则

### 发布与报名

企业活动发布 → 运营审核通过 → 学生个人报名 → 主办方资格审核 → 建队/接受邀请。

运营自办活动发布 → 内部审核通过 → 学生个人报名 → 运营资格审核 → 建队/接受邀请。

已通过报名不能通过重新 POST 降回待审。已归档活动不可继续报名。取消后重新报名仍检查容量。竞赛报名通过不生成“完成认证”。

### 团队

- 同一学生在同一竞赛只能属于一个团队，数据库复合主键兜底。
- 队长创建团队，队员自行注册并报名通过后接受邀请。无需共享密码。
- 邀请绑定登录邮箱，有效期最长 7 天，且不超过组队截止；保存摘要而非明文邀请码，单次使用、可撤销。
- 提交前且组队期内队员可退出；队长不能直接退出；需要更换队长时由项目团队人工核实处理，当前无自动转让入口。
- 提交后名单冻结，补交成果不重新开放换人。
- 建队和加入等多表写入用事务；团队 version 与 mutation_key 防止并发覆盖。

### 成果与评审

`forming → submitted → revision_requested → submitted → completed / awarded`

队长填写成果名、完成过程/验证/产出及可选 http(s) 成果链接；成员可查看。第一版采用文本和外部成果链接，不新增不受控的私密文件上传渠道。

提交前检查人数、截止时间、角色及版本。评审只处理 submitted，主办方填写意见，可选 0–100 分；获奖必须填奖励说明。要求补充时允许原团队在截止后补交。最终评审不允许重复覆盖，修正争议需要人工核实并保留审计。

每次提交/评审保存历史，不覆盖历史版本。终审为成员生成独立认证经历；其 source_id 绑定团队，重复操作不能生成重复记录。初始 is_public=0，避免企业敏感成果被自动公开。学生可自行决定成长主页可见性。

## 6. 数据模型与持久化

| 表 | 关键字段 | 约束 |
|---|---|---|
| workspace_records | id, owner_id, kind, payload, version, archived_at | 活动规则及发布主体 |
| activity_registrations | activity_id, student_owner_id, publisher_owner_id, answers, status | 每学生每活动一条报名 |
| challenge_teams | id, activity_id, captain_id, name, status, submission, review, version, mutation_key | 乐观锁；当前成果/结果快照 |
| challenge_members | activity_id, student_id, team_id | PRIMARY KEY(activity_id,student_id) |
| challenge_invites | team_id, email, token_hash, expires_at, consumed_at, revoked_at | 邀请摘要唯一 |
| challenge_history | team_id, actor_id, action, payload, created_at | 追加式提交/评审历史 |
| student_experiences | student_id, source_type, source_id, certified, is_public | 来源唯一，默认私密 |
| audit_logs / notifications | 操作者、动作、目标；接收人及状态 | 留痕与结果通知 |

所有正式记录保存在服务器 SQLite 数据库，不使用浏览器 localStorage 作为正式数据源。浏览器草稿只是辅助恢复，不等同于提交成功。新增表进入既有数据库整体备份，无需新增云数据库。

## 7. 界面规范

颜色沿用青蓝、蓝黑、淡冰蓝与少量黄色，不新增大面积红色。竞赛发布、任务书和结果在三端使用共享组件。表单 16px，输入错误明确显示，提交中禁用重复操作，失败保留输入。抽屉内部滚动，不把完整任务书挤到屏幕之外。

公司 Logo 使用固定外框与 object-fit:contain，不按原图比例伸缩。列表长标题/摘要限定行数；完整文本可在详情中阅读。内容封面统一比例，卡片操作区底部对齐。动效仅对展开面板轻量进入，遵循系统减少动态效果设置。

## 8. 验收要求

1. 企业/运营各自发布竞赛，未经审核不公开。
2. 未登录、未报名、未通过资格不可建队或加入。
3. 邀请邮箱不符、过期、撤销、重复使用均失败。
4. 人数不足不可提交、超员不可加入、同活动不能多队。
5. 队员不能代表队长提交；其他企业不能看见或评审成果。
6. 提交后不能变更名单；重复/过期版本请求不覆盖数据。
7. 主办方退回补充、队长补交、终审后所有成员看见同一结果。
8. 每位成员仅生成一条对应认证，默认私密；未终审不提前认证。
9. 服务重启后团队、邀请状态、历史和认证仍存在。
10. 三端实际浏览器检查输入持续性、弹层、按钮、长文本及错误反馈。

## 9. 不应靠猜测承诺的运营规则

本次保守默认：不自动付款、不保证录用、不自动公开团队作品；不清洗/删除现有真实记录，不为旧活动批量补造竞赛结果。

正式举办前主办方仍须在任务书明确知识产权、可使用的数据及授权、奖金领取与税费责任、未成年人参与安排、撤赛/取消与评审争议处理。这些需要实际运营规则，不能由代码代替企业承诺。

尚需单独迭代的已有机制：普通活动的“报名认证”与“实际完成认证”语义仍应进一步拆分；历史示例内容真实性应由运营逐条核验；大规模多评委评分、跨队人员转让、在线奖金结算不属于本次已确认范围，未伪装成现成功能。

## 10. 工程检查与依赖边界

新增 `npm run typecheck`，使独立 TypeScript 检查与 ESLint、构建、自动测试共同作为发布检查。补齐运行时数据库/文件存储类型，修复可选标签缺失造成的内容列表异常。

React、React DOM 和 React Server DOM Webpack 同步到 19.2.8，image-size 固定到 2.0.4，Vite 更新到 8.0.16，并更新可兼容的间接依赖。相关上游通告：[React 服务端拒绝服务修复](https://github.com/advisories/GHSA-wx67-qw84-cm4g)、[图片解析拒绝服务修复](https://github.com/advisories/GHSA-w3rx-r6r6-pgpr)。

2026-09-22 完整 npm 审计仍报告 10 项工具链依赖告警（6 high、4 moderate），涉及本地 Cloudflare/Wrangler/Miniflare 和 drizzle-kit 链路；不能据 `--omit=dev` 的结果宣称全项目无漏洞。此次腾讯云发布使用独立 Node 产物，不部署这些开发服务。没有使用 `npm audit fix --force` 强行降级 drizzle-kit 或跨范围升级 Cloudflare；后续工具链升级应单独验证。开发服务不得对公网开放。

当前成果工作台最多读取最近 500 个团队；规模达到该上限前应增加服务端分页与筛选，不能把此版本当作无限规模系统。成果编辑在点击提交成功后持久化，尚未提供服务器草稿自动保存，长篇成果宜在外部文档整理后提交链接。
